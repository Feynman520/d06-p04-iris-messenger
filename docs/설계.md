# IRIS 메신저 — 설계 (조각 점검 기록)

작성 2026-09-11. 설계 우선 원칙에 따라 조각별로 사용자 확정을 받은 내용만 적는다. 미확정 조각은 "미착수"로 둔다.

## 0. 배경·결정

- 목적: Face 사용자끼리 소통. 최종 목표는 **에이전트끼리 소통**(2차). 1차는 사람→사람 글·파일만.
- 정체성: IRIS 패키지(무료·오픈소스·설치형) = 본체, 메신저 = 꽂아도 되고 안 꽂아도 되는 **확장 모듈**. 본체는 모듈을 모른다.
- 서버는 사용자 작업 내용·과정·세션 기록을 절대 받지 않는다. 메시지는 E2EE 암호문으로만 지난다. 서버가 아는 것 = 이메일·표시 이름·공개 열쇠·연락처 관계·"누가 누구에게 언제 몇 번"(메타데이터, 처리방침에 명시).
- 결정 6 + 추가: 기반 A 자체 허브(Supabase) / 1차 글·파일 / E2EE 처음부터 / 이메일 OTP(Supabase 매직링크 메일에 실린 6자리 숫자, 링크 클릭은 안 씀 — 조각 3) / 초대 코드 상호 수락 / 공식 허브 무료 시작 + 서버 주소 칸 / 사용자당 열쇠 하나 + 백업 문구 / 모듈 = 별 프로세스 / 불변 = 모듈 없는 Face는 네트워크 호출 0.
- 폴더: P04 하나(module + hub). `hub\`는 `module\`을 참조하지 않는다. 다음 모듈이 생기면 `hub\`를 새 P로 뗀다. Face(P02)에는 접점(콘센트)만 남는다.

## 조각 1 — 경계·접점 계약 (확정 2026-09-11)

- 데몬 시작 때 `modules\` 탐색 → `module.json`의 계약 버전 확인 → 자식 프로세스로 실행(PID 기록, 종료는 그 PID만) → stdio JSON 한 줄씩, 허용 목록만 통과 → ⏻ 때 `shutdown`.
- 허용 목록 v1: 코어→모듈 `hello`(계약 버전·설정 폴더·언어·테마(다크/라이트·강조색, 조각 7). 세션·폴더·기록·사용자 이름·이메일은 주지 않음)·`shutdown` / 모듈→코어 `panel`(127.0.0.1:포트 화면 주소, 서랍 자리 iframe)·`badge`(안 읽은 수)·`notify`(title·sub·target — notify.js 경유, 누르면 서랍을 열고 target으로)·`queue`(v1은 받되 무시 — 2차 자리).
- 모르는 말은 버리고 로그만. "세션에 글 넣기"는 계약에 없다.
- 증명: `scripts\verify-nomodule.mjs` — 모듈 없이 데몬을 띄우고 데몬 PID의 바깥 연결(127.0.0.1 제외) 0개 확인.
- 솔직한 한계: 별 프로세스는 버그 격리이지 악의 격리가 아니다(같은 OS 사용자 권한). 악의 모듈 방어 = 조각 8(출처 서명). 문서에 명시.
- 계약 버전 불일치 → 안 싣고 설정 화면에 한 줄 안내. 모듈 사망 → 재시작 3회, 그 뒤 배지 ⚠, 코어 영향 0.
- 예약: `module.json`에 요구 등급(0 본체 정보 없음 / 1 세션 상태 읽기 / 2 세션에 요청 넣기)을 적는 자리. v1 코드는 0등급만 구현.
- 정본 = P02 `docs\모듈-계약-v1.md`(작성 예정).

## 조각 2 — 허브 서버 (확정 2026-09-11)

- Supabase 부품 4: Auth(OTP 메일, 이메일은 여기에만) · Postgres(표 5) · Realtime(새 메시지 벨, private 모드로 RLS 준수) · Storage(암호화 파일, 10MB 상한 — 조각 9).
- 표(최종, 뒤 조각의 추가 칸 반영): `profiles`(사용자 번호·표시 이름·공개 열쇠·`key_version`) · `invites`(코드·만든 이·만료·쓴 이) · `contacts`(나·상대·상태 대기/수락/차단·요청한 쪽) · `messages`(`client_id` UNIQUE·보낸 이·받는 이·암호문·종류 글/파일·파일 위치·보낸 시각·배달 시각) · `meta`(`schema_version`). 파일 이름·크기 힌트는 암호문 안에.
- RLS 3규칙: 메시지는 내가 보낸/받은 것만 · 새 메시지는 수락된 연락처에게만(스팸 구조적 차단) · profiles/contacts는 나와 수락된 연락처만.
- 오프라인 보관 = 표 자체. 배달 후 30일 지나면 서버 자동 삭제(정본은 각자 PC). 1:1 전용, 그룹은 2차 별 표.
- 열쇠: anon key는 모듈에 배포 가능(RLS가 방어) / service role key는 운영자 secrets에만.
- 증명: `verify-rls.mjs` — 가짜 사용자 2명으로 서로의 줄을 읽어 0행 확인. 정책 바꿀 때마다 실행.
- 탈퇴: Auth 사용자 삭제 → 표 4의 내 줄 연쇄 삭제(CASCADE).
- 섬 문제(서버 주소 칸이 다르면 대화 불가)는 의도된 제약으로 문서화.
- 사용자당 공개 열쇠 하나(기기 이전은 백업 문구, 조각 4).

## 조각 3 — 신원·로그인 (확정 2026-09-11)

- 방식: 이메일 → 6자리 OTP(만료 10분, 5회 오류 잠금) → access(1h)+refresh 토큰. **링크 클릭 방식은 쓰지 않는다**(브라우저에 토큰이 떨어져 `iris-face://` 레지스트리 등록이 필요 → 무접촉 위반). Supabase 메일 틀에 링크·숫자 둘 다 넣어 추가 비용 0.
- 토큰 보관: refresh 토큰을 윈도 DPAPI로 잠가 모듈 `state\`(git 제외)에 저장. DPAPI 호출은 PowerShell `ProtectedData`(네이티브 모듈 없음 → Smart App Control 함정 회피). 한계: 같은 윈도 사용자의 악성코드에는 무력 — 다른 사용자·다른 PC·백업 파일에서 못 푸는 것까지가 약속.
- 첫 로그인: 표시 이름 입력 → profiles 한 줄(열쇠는 조각 4).
- 로그아웃 = 토큰 삭제+서버 폐기(열쇠·메시지는 남음) / 탈퇴 = `delete_me` 함수 → 표 4 연쇄 삭제 + 로컬 전부 삭제 / 서버 주소 변경 = 자동 로그아웃 / 모듈 제거 = 폴더 삭제(토큰·열쇠·메시지 전부).
- 미로그인·오프라인: 모듈 화면에 로그인 버튼만. 본체 영향 0.
- 다기기: 로그인은 허용, 열쇠 없는 기기는 "백업 문구로 복원" 안내(로그인과 읽기 권한 분리).
- 이메일 변경은 1차 제외(탈퇴 후 재가입).
- 운영 항목으로 이관: Supabase 내장 SMTP는 시간당 몇 통이라 실사용 불가 → 자체 SMTP(Resend 무료 월 3,000통 등) = 조각 9 첫 항목.

## 조각 4 — E2EE 열쇠 (확정 2026-09-11)

- 사용자당 열쇠 한 쌍. 첫 로그인 때 12단어 시드 생성 → 개인 열쇠 → 공개 열쇠 유도(같은 12단어 = 같은 열쇠). 공개 열쇠는 `profiles.public_key`, 개인 열쇠는 DPAPI로 잠가 모듈 `state\`. 개인 열쇠·12단어는 서버에 절대 안 감.
- 백업 문구: 12단어를 한 번 크게 보여주고 "적어 두셨습니까" 확인. **복사 버튼 없음**(클립보드 잔류 방지). 설정 → 다시 보기는 로그인 상태 + 확인 클릭 뒤에만.
- 암호화 부품(Node 내장 `crypto`만, 외부 의존 0): X25519 키 합의 2회(내 개인×상대 공개 = 발신자 인증 / 일회용 개인×상대 공개 = 메시지별 자물쇠) → HKDF → AES-256-GCM. 암호문 = 일회용 공개 열쇠 · nonce · 암호문 · 태그. 파일은 임시 대칭 열쇠로 잠가 Storage에, 그 열쇠·파일 이름·크기는 메시지 암호문 안에(서버는 파일 이름도 모름).
- 서버의 열쇠 바꿔치기(MITM) 방어: 초대 코드에 공개 열쇠 지문(8자리) 포함 → 상대가 서버에서 받은 열쇠와 대조, 불일치면 수락 거부(상세 조각 5). 초대 코드는 서버 밖으로 전달.
- 분실: PC 교체+12단어 있음 → 복원(지난 메시지는 옛 PC에만, 서버는 30일 뒤 삭제) / 12단어 없음 → 지난 메시지 영구 상실, "열쇠 재설정" = 새 12단어·새 공개 열쇠 + `profiles.key_version` +1 → 연락처 화면에 "열쇠 바뀜, 지문 재확인" 경고 자동 / 12단어 유출 → 즉시 재설정.
- 조각 2 표 반영: `profiles`에 `key_version` 칸 추가.
- 로컬 저장: 풀린 메시지는 PC에 평문 저장(Face 세션 기록파일과 같은 기준). 문서에 명시.
- 솔직한 한계(README에 명시): 검증된 부품의 조립(ECIES 계열)이며 외부 감사 없음 · 전방 비밀성은 절반(수신자 개인 열쇠 유출 시 지난 메시지 열림, 더블 래칫은 1차 제외) · 열쇠 주기 회전 1차 제외(재설정만).

## 조각 5 — 연락처 (확정 2026-09-11)

- 원칙: 양쪽 상호 수락으로만 줄이 생긴다. 이메일 검색 없음. 미수락 상대에게는 RLS가 메시지 자체를 거부.
- 초대 코드 `IRIS-XXXX-XXXX-FFFF`: 앞 8자 무작위(서버 `invites`에 등록, 만료 7일, 1회용, 미사용 최대 10개) + 뒤 4자 = 내 공개 열쇠 지문 일부(로컬에서 붙임, 서버 미등록). 서버 밖(카톡·말)으로 전달.
- 흐름: 코드 생성 → 전달 → 상대가 입력 → 상대 모듈이 서버에서 주인 표시 이름·공개 열쇠 조회 → 지문 4자 대조(불일치 거부) → `accept_invite` 서버 함수(원자적: 코드 사용됨 + contacts 대기 줄 생성, 호출자 기준 분당 5회 제한) → 주인 화면에 요청 표시(표시 이름·지문) → 수락/거절 → 양쪽 상대 공개 열쇠를 로컬에 고정(pinning; 이후 서버 값이 다르면 ⚠만, 로컬 것 사용).
- 차단: 상태 "차단" → RLS가 그 사람의 메시지 거부. 상대에겐 전송 실패만 보임.
- 화면: 목록(표시 이름·지문 4자·상태·열쇠 바뀜 ⚠) / 상세(지문 8자 전체 + "직접 대조하세요"). 이름은 흉내 낼 수 있으니 신뢰 근거 = 코드 전달 경로 + 지문임을 문구로 반복.
- 1차 제외: 그룹·검색·QR(카메라 필요, 2차).

## 조각 6 — 메시지 흐름 (확정 2026-09-11)

- 보내기: 글 4,000자 / 파일 10MB(조각 9에서 20→10MB로 하향, 송출 한도) → 로컬 `client_id` 생성(서버 `messages.client_id` UNIQUE, 조각 2 표에 칸 추가) → 암호화(파일은 먼저 잠가 Storage에 올리고 열쇠를 편지 안에) → INSERT → 성공 시 서버 시각 / 실패 시 outbox 보관·재시도, 3회 실패(차단 등)면 "보낼 수 없음"으로 중단.
- 받기: 모듈 프로세스가 Realtime 웹소켓 구독 + **접속·재접속마다 미배달(배달 시각 없음) 조회로 빈틈 메우기(필수 검증 항목)** → 복호화 → 로컬 저장 → 배달 시각 기록 → 코어에 `badge`(안 읽은 수)·`notify`(**보낸 이 이름만**, 내용 없음).
- 저장: 내 PC `state\messages\<상대>.ndjson`(평문, 한 줄 = 한 편지, 정본) · `state\files\`(풀린 파일) / 서버 messages·Storage = 배달 후 30일 삭제, 미배달 메시지는 보존, Storage 파일은 미배달이어도 90일에 삭제(명시).
- 연결(모듈 프로세스 소유, 코어 무관): 지수 백오프 1→60초 재연결, 절전 복귀 동일, 웹소켓 3회 연속 실패 시 60초 폴링(10분마다 웹소켓 재시도, 화면 "느린 연결"). 상태 점 초록/노랑(outbox N)/회색(미로그인).
- 파일 받기: 자동 다운로드 없음(받기 버튼) · 실행 파일 확장자(.exe·.bat·.ps1·.cmd·.js 등) 빨간 경고.
- 1차 제외: 읽음 표시·상대 쪽 삭제·편집·인용·반응. 로컬 삭제만. 로컬 저장은 ndjson으로 시작, 대량화 시 `node:sqlite`.

## 조각 7 — 화면·알림 (확정 2026-09-11)

- 방식 = 지금 TeamClaude 한도 서랍(Ctrl+D, 오른쪽 서랍 iframe)과 동일. 차이는 ① 주소를 모듈이 `panel` 말로 알려 줌(데몬이 살리지 않음) ② 버튼이 모듈마다 1개 + 배지. Face 콘센트의 화면 쪽 = 기존 서랍 코드를 "주소·버튼 여러 개"로 일반화.
- Face 쪽: 헤더 버튼(아이콘+배지, 99+ 상한) · 서랍 재사용(한 번에 하나, 끌어 조절, 기본 반폭) · 단축키 Ctrl+Shift+M(첫 모듈만; Ctrl+M은 🎤 음성이 이미 사용, 2026-09-11 구현 때 변경) · Esc 닫기(before-input-event 중계로 iframe 초점에서도) · 데몬 `features.modules: [{name,label,icon,panel,badge}]` + 웹소켓 방송.
- 초점: 서랍은 사용자가 연 것이므로 iframe에 초점 허용, **닫을 때 Face 입력창으로 초점 복귀**. 모듈 안에서는 Esc를 쓰지 않는다(대화상자는 ✕만) → Esc 충돌 없음.
- 모듈 화면: 모듈 프로세스 안 HTTP 서버가 단일 HTML 제공. 127.0.0.1 + 무작위 포트 + 시작 때 1회용 토큰(`?t=`)으로 다른 프로그램 차단. 좌: 연락처(안 읽은 수·상태·열쇠 ⚠)·초대 코드·설정(계정·서버 주소·백업 문구·로그아웃·탈퇴)·연결 점 / 우: 대화(파일은 받기 카드)·입력(Enter 전송, Shift+Enter 줄바꿈). 미로그인 = 이메일→코드 두 화면. 알림·확인은 모듈 자체 대화상자(네이티브 금지 규칙 동일).
- 테마: 코어 `hello`에 `theme`(다크/라이트·강조색) 1칸 추가(조각 1 반영).
- 알림: 모듈 `notify {title: 보낸 이, sub: "새 메시지"}` → 코어 notify.js(초점 안 뺏음·창 뒤면 OS 알림·설정으로 끄기) → 누르면 모듈 서랍 열고 그 상대로. 같은 상대 연속 알림은 1분 1회로 묶음. 내용은 어디에도 안 나감.
- 1차 제외: 별도 창(pop-out).

## 13. 구현 때 바뀐 것(2026-09-13)

설계와 실제 구현 사이에 생긴 차이 8가지. 이전 조각(1~12)은 사용자 확정 기록이라 손대지 않고, 바뀐 부분만 여기에 새로 적는다.

① **`supabase-js` 번들 대신 손으로 짠 최소 REST 클라이언트.** 조각 8은 "esbuild 단일 번들, supabase-js 포함"을 전제했으나, 실제로는 `hub/client/supa.mjs`가 GoTrue(OTP)·PostgREST·Storage·Realtime을 fetch만으로 직접 호출하는 외부 의존 0의 최소 클라이언트로 작성됐다. supabase-js의 기능 대부분(세션 자동관리·타입 등)이 이 프로젝트 규모에는 과했고, 빌드 단계 없이 파일을 그대로 배포할 수 있다는 이점이 더 컸다. `npm run build:zip`은 여전히 필요하지만(서명·manifest 때문) 번들러 자체는 더 이상 필수가 아니다.

② **로그인 잠금이 두 겹(로컬 5회 + 서버 분당 10회)으로 나뉘었다.** `hub/client/session.mjs`는 OTP 5회 연속 실패 시 그 기기에서 로컬 잠금을 건다(조각 3의 "5회 오류 잠금"). 이와 별개로 `0002_hardening.sql`의 `note_invite_attempt()`는 초대 코드 조회·수락에 분당 10회 서버 스로틀을 건다(조각 5는 원래 "분당 5회"를 언급했으나 실제로는 `lookup_invite`+`accept_invite`를 합쳐 분당 10회로 완화·통합했다). 두 잠금은 서로 다른 기능(로그인 vs 초대 코드)에 걸리는 별개 메커니즘이며 공유 카운터가 아니다.

③ **Storage 90일 청소는 SQL `cleanup()`이 아니라 운영 스크립트가 맡는다.** 조각 9의 "Storage 파일은 미배달이어도 90일에 삭제"는 애초에 `pg_cron` 안의 `cleanup()` 함수에 넣는 안도 검토됐으나, Supabase 무료 플랜은 `pg_cron`으로 Storage API(파일 실체 삭제)를 직접 호출할 수 없어(SQL은 `storage.objects` 메타데이터 행만 건드릴 수 있고, 실제 파일 바이트 삭제는 Storage REST API가 필요) `hub/server/ops/daily.mjs`가 별도로 만들어졌다: SQL로 90일 지난 객체 이름을 조회한 뒤 service-role Storage API `DELETE /storage/v1/object/files`(배치 100개)로 실제 삭제한다. `messages`·`invites`·`invite_attempts`는 여전히 `public.cleanup()`(SQL만으로 충분) 그대로다.

④ **매직링크를 붙여넣는 로그인 경로가 추가됐다.** 조각 3은 "링크 클릭 방식은 쓰지 않는다"를 확정했지만, 실제 `session.mjs`는 6자리 숫자 입력 외에 매직링크 URL을 통째로 붙여넣어 그 안의 토큰으로 인증하는 보조 경로도 지원한다(`type: 'magiclink', token_hash: tokenHash`). 이는 "링크를 브라우저에서 클릭"하는 것과는 다르다 — 사용자가 메일의 링크 텍스트를 복사해 모듈 화면에 붙여넣는 것으로, `iris-face://` 같은 커스텀 프로토콜 등록이 여전히 불필요해 무접촉 원칙은 유지된다. 순수 숫자 입력이 안 되는 메일 클라이언트 환경을 위한 대비책이다.

⑤ **0002_hardening 마이그레이션이 조각 2·5에 없던 항목을 추가로 끼워 넣었다.** `verify-rls.mjs`로 실제 검증하는 과정에서 드러난 구멍 3가지를 0001 배포 뒤 별도 마이그레이션으로 막았다: (a) `respond_contact`에서 차단당한 쪽이 `unblock` 없이 `block`을 다시 불러 상대의 차단을 뒤엎는 우회 방지, (b) 초대 코드 추측 방지용 `invite_attempts` 표 + `note_invite_attempt()`(②의 서버 스로틀), (c) 파일 메시지의 `file_path`가 보낸 사람 자신의 폴더인지 검사하는 정책과 `kind`/`file_path` 정합성 제약(`messages_kind_file_path`). 0001_init.sql 자체는 이미 배포된 파일이라 고치지 않고 0002로 별도 적용했다(반복 실행 가능).

⑥ **열쇠 불일치(`keyMismatch`)의 유일한 출구는 "12단어 복원" 또는 명시적 확인을 거친 "열쇠 재설정" 둘뿐이다.** 조각 4는 "열쇠 재설정 = 새 12단어·새 공개 열쇠 + `key_version` +1"까지만 정했으나, 구현에서는 이 상태에서 사용자가 실수로 아무 버튼이나 눌러 재설정해 버리는 것을 막기 위해 `panel.html`이 `S.keyMismatch`일 때 화면을 강제로 `identity` 단계로 돌리고, 일반 로그인 화면(`idn-normal`)과 새 계정 생성 화면(`idn-create`)을 모두 숨긴 뒤 12단어 복원 칸과 "확인 대화상자를 거친 재설정" 버튼만 보여준다("물어보지 않고 누를 수 있는 단추로 두면 안 된다"). 재설정을 누르면 "예전에 받은 글은 다시 열 수 없고, 연락처마다 내 새 지문을 다시 확인해야 합니다"라는 경고 확인을 반드시 거친다.

⑦ **파일 전송 실패는 outbox 자동 재시도에 들어가지 않는다.** 조각 6은 글 메시지의 outbox 재시도(3회 실패 시 중단)만 정했고 파일은 구분하지 않았으나, `module/messages.mjs`는 파일을 Storage에 올리는 단계가 끝나기 전에는 그 편지를 outbox 재시도 목록에 넣지 않는다("파일이 아직 Storage에 없는데 INSERT만 재시도하면" 안 됨) — 즉 파일 업로드 자체가 실패하면 자동 재시도 없이 그 자리에서 멈추고, 파일이 Storage에 자리 잡은 뒤의 메시지 행 INSERT만 outbox 재시도 대상이 된다. 사용자에게는 업로드 실패 시 다시 보내기를 직접 눌러야 한다는 뜻이며, 화면 문구로 안내한다.

⑧ 실시간 `online`은 구독 ack(phx_reply ok) 뒤에만 켜진다(2026-09-13 라이브 실측 뒤 수정). 그 대신 **ack 직후 ms 창은 2초 뒤·2분마다 gapFill이 메운다** — 구독이 받아들여지는 그 순간에 서버에 들어온 줄은 도어벨을 울리지 못하므로, 연결된 뒤 2초에 한 번 더 훑고 연결돼 있는 동안 2분마다 한 번씩 훑는다(끊기면 이 두 타이머는 거두고 `slow` 폴링이 그 자리를 맡는다).

⑨ **화면 개편(v0.2.0, 2026-09-13 사용자 확정).** 로그인 방식은 조각 3의 이메일 OTP 그대로 두되(사용자 재확인: "자주 로그인할 필요가 없고 자동 로그인이라면 이메일+코드가 훨씬 편하다", 보안성은 비밀번호 방식과 같음), 낯설게 느껴진 원인이 화면 문구였으므로 문구를 한국어 사용자에게 익숙한 "인증번호" 흐름으로 바꿨다: 시작하기 → 인증번호 입력(6칸, 다 차면 자동 확인; 링크 붙여넣기는 "메일에 숫자가 없나요?" 접힘 아래) → 상대에게 보일 이름. 제목은 Face 헤더와 같은 회전 육각 + IRIS(문 화면에는 작은 "메신저" 한 단어 추가). 본 화면은 왼쪽 줄 위 브랜드 · 연락처 제목 옆 + 메뉴(초대 만들기/입력) · 아래 내 이름·지문·연결 점·⚙ / 상대 머리는 이름 + 지문 칩 한 줄 + … 메뉴(차단·삭제) / 말풍선은 테두리 없이 같은 사람 연속 글 묶음·날짜 구분선 / 입력창은 둥근 칸 + 📎·➤ 아이콘, 글자 수는 상한 500자 전부터만. 설정은 계정·열쇠·알림·서버·정보 다섯 묶음, 위험 동작(로그아웃·열쇠 재설정·탈퇴)은 맨 아래. 파일은 `panel.html`(뼈대)·`panel.css`·`panel.js` 셋으로 나누고 `panel.mjs`가 서버 기동 때 한 장으로 조립한다(바깥 자원 0·CSP·토큰 문지기 그대로). 처리방침 링크는 `id="link-privacy"` 한 곳 — 공식 홈페이지가 생기면 그 주소로 바꾼다. 구글 등 소셜 로그인은 붙이지 않았다(필요해지면 브라우저 → 127.0.0.1 되돌아오기 방식으로 가능함을 확인만 해 둠).
