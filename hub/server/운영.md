# hub/server — 운영 (Operations Runbook)

`docs/설계.md` 조각 9(운영)를 실제로 수행하는 절차서입니다. 모든 주기는 "며칠 안 해도 버티는" 기준으로 잡혀 있습니다. 키·토큰 값은 여기에 절대 적지 않고, `secrets .env`의 **이름**만 적습니다(실제 값 = `$env:CLAUDE_CONFIG_DIR\secrets\.env`).

## ① SMTP (로그인 메일 발신)

- **언제**: 최초 배포 시 1회, 이후 발신 도메인이 바뀔 때만.
- **무엇**: Supabase 내장 메일은 시간당 몇 통뿐이라 실사용에 부족 → Resend(무료 월 3,000통)로 대체.
- **어떻게**: Resend에서 발신 도메인 검증 → `.env`에 `RESEND_API_KEY`·`IRIS_MESSENGER_MAIL_FROM` 추가 → `npm run deploy:hub`가 Supabase Auth SMTP 설정을 패치.
- **계정 이름**: Resend 계정(운영자 개인) / secrets 키 이름 `RESEND_API_KEY`, `IRIS_MESSENGER_MAIL_FROM`.

## ② 무료 프로젝트 깨우기 (7일 미사용 정지 방지)

- **언제**: 3일마다 자동(사람 개입 없음).
- **무엇**: Supabase 무료 프로젝트는 7일간 API 호출이 없으면 자동 정지된다 → 정지 전에 가벼운 조회 1회로 활성 상태를 유지.
- **어떻게**: `.github/workflows/keepalive.yml`(GitHub Actions, cron `23 4 */3 * *` + 수동 실행 `workflow_dispatch`)이 `module/hub.json`의 `url`·`anonKey`로 `GET /rest/v1/meta?select=key`를 호출.
- **계정 이름**: GitHub Actions에는 **anon key만** 들어간다(공개돼도 안전 — RLS가 방어). 관리 토큰(PAT)은 절대 GitHub에 두지 않는다.

## ③ 한도 감시

- **언제**: 운영자 PC에서 필요할 때 수동 실행, 또는 정기 예약 작업으로 등록(아래 참고).
- **무엇**: 무료 플랜 한도 — DB 500MB · Storage 1GB · 월 송출(egress) 5GB · 가입자 50,000명. 80%를 넘으면 경고.
- **어떻게**: `node hub/server/ops/daily.mjs`가 Management API(PAT)로 `pg_database_size`·`storage.objects` 합계·`auth.users` 수를 조회해 백분율을 출력하고, 80% 초과 시 stderr에 `WARN`을 남긴다. 윈도 작업 스케줄러 등록 예시:
  ```
  schtasks /create /tn "IRIS-Messenger-ops-daily" /tr "node \"<repo>\\hub\\server\\ops\\daily.mjs\"" /sc daily /st 09:00
  ```
- **계정 이름**: Management API PAT = secrets 키 `SUPABASE_ACCESS_TOKEN_FEYNMAN520`(GitHub에는 절대 두지 않음, 운영자 PC의 예약 작업에서만 읽음).

### 참고 — 초대 코드 잠금창 관련 확정 사항 (2026-09-13 마무리)

`lookup_invite`(초대 코드 조회)와 `accept_invite`(초대 코드 수락)는 `hub/server/migrations/0002_hardening.sql`의 `note_invite_attempt()`로 **분당 시도 횟수를 합산**해서 관리한다. `lookup_invite`는 10회를 넘으면 함수 안에서 `raise exception`으로 실패하며, 이 예외는 **트랜잭션 전체를 롤백**시키므로 방금 `note_invite_attempt()`가 기록한 시도 행 자체도 되돌아간다 — 즉, **막힌(rate-limited) `lookup_invite` 호출은 그 자체로는 1분 잠금창을 다시 늘리지 않는다**(잠금창이 계속 갱신되며 영원히 안 풀리는 사고를 막기 위한 의도된 설계). 반면 `accept_invite`는 예외 대신 `'rate_limited'` 상태값을 정상 반환하므로 그 호출의 시도 행은 그대로 남는다 — 두 함수의 거동 차이는 의도된 것이며, 정책을 바꿀 때는 `scripts/verify-rls.mjs`의 관련 검사(분당 10회 초과 검증)를 다시 통과시킨다.

## ④ 백업

- **언제**: 주 1회.
- **무엇**: Postgres 전체를 덤프해 서버 장애·실수 삭제에 대비.
- **어떻게**: 운영자 PC에서 `supabase db dump`(Supabase CLI)를 실행해 로컬 디스크 + 외장 저장소 두 곳에 보관. **2주 연속으로 실행하지 못하면** 그 사실을 알아챌 수 있도록 별도 야간 백업 로그에 경고를 남긴다.
- **참고(범위 밖 명시)**: 이 저장소는 백업 자동화 스크립트를 아직 포함하지 않는다 — Supabase CLI 설치·자동 스케줄링은 후속 작업으로 남겨둔다(설계 브리프에서 명시적으로 범위 밖 처리).
- **계정 이름**: Supabase CLI 로그인 = 운영자 Supabase 계정(`FEYNMAN520`).

## ⑤ 리전

- **언제**: 프로젝트 생성 시 1회만 선택 가능(이후 변경 불가).
- **무엇**: 서울(`ap-northeast-2`) 고정 — 한국 사용자 지연 최소화.
- **어떻게**: Supabase 대시보드 "New Project"에서 Region을 `ap-northeast-2 (Seoul)`로 선택.
- **계정 이름**: 해당 없음(프로젝트 생성 시 1회성 선택).

## ⑥ 처리방침·나이 확인

- **언제**: 서비스 운영 중 상시(문서), 사용자가 로그인할 때마다(체크박스).
- **무엇**: 수집·미수집·보관 기준을 `hub/server/처리방침.md`에 명시하고, 로그인 화면(`out` 단계)에 "만 14세 이상이며 처리방침을 읽었습니다" 체크박스를 둔다.
- **어떻게**: `module/panel.html`의 `out-agree` 체크박스가 체크되기 전에는 로그인 버튼이 비활성화된다. 사용자 수가 수십 명을 넘으면 처리방침을 전문가(법률 자문)에게 검토받는다.
- **계정 이름**: 해당 없음.

## ⑦ 종료 절차

- **언제**: 허브 운영을 그만두기로 결정한 시점.
- **무엇**: 사용자가 자기 데이터를 잃지 않고 대비할 시간을 준다.
- **어떻게**: ① 모듈 화면에 30일 전 종료 공지 ② 사용자가 연락처를 내보낼 수 있는 창구 안내 ③ 30일 뒤 DB 전체 삭제.
- **계정 이름**: 해당 없음.

- **언제**: 서명 개인 열쇠 유출이 의심되거나 확인될 때.

- **계정 이름**: 서명 개인 열쇠 = 운영자 secrets에만 보관, 저장소 어디에도 커밋하지 않음.
